Create a DOM object

The following Elements create an extra DOM object (if this is new 1 maybe I need to add an intro again):

  • IFRAME, and FRAMESET ~ use discouraged.
  • Adding an SVG image 2 as OBJECT or IMG elements ~ not inline tags.
  • MathML 3 4 as self declared is a type of XML used for rendering Maths equations, see example draw-equations-inline.
    • something XML ~ I never used this in-page. RSS etc is an XML doc, but that's a separate file and URL.
  • WebComponent / ShadowDOM creates an extra DOM of sorts, see webcomponent-maquette as a worked example.
    • NB: a plain component via React, Vue or Angular etc isn't a sub document, its clearly in the main DOM.
  • There are 3 more JS engine options. This DOMParser().parseFromString() 5 is the best security choice.
  • a HTMLIsland / TEMPLATE element 6 7 8 is like a sub document, but technically isn't complete. Some people hydrate SSG HTMLIslands on the client side. I assume they are doing the work in a Worker Object then passing the HTMLElement back to the first DOM.
  • A different process is Range.createContextualFragment 9.
    • Looking at sub-page interactions, a TEMPLATE element can be used to transmit sub-documents eg a large interstitial containing a simplified user-guide. That TEMPLATE object is written into the initial HTML doc inline.
  • With an object in current scope, OBJECT.createClone(true) 10 will make a new one.
  • A JS string template (ie with back-ticks) can be used to transmit data, but isn't a DOM object. Relevant CSS and a container Element, OR DIALOG with modal, set can make a modal interaction, so feel like a separate DOM object (but its the same).
  • A legacy solution that was widely used, is to put a string containing HTML into a jQuery constructor. This module API is deprecated.
  • Something to create a new browser tab, as a full UI object (JS script, scripted input from Puppeteer etc).

Aside: I have many UI tests that need to create or pass DOM objects, only these are hosted inside Node.

Applying that DOM object

Obviously your DOM object will probably have a URL attached, and so a volume of data. This section is blurry on tab vs window vs DOM object, but they are largely interchangeable. In the same DOM object, we can use JS to inject further elements. This is in 1 Domain / security context, and simple to visualise. That sentence assumes the JS came from the same server that the page is from. In most situations, only a single DOM implies less RAM is used. Any solution that launches a separate Electron App is multi-DOM, and is also much less efficient.
Some websites are designed to have multiple windows, my current bank for example loads secure data in a fresh tab/ DOM object. Alternatively, we might need scale, remembering that features using multi-domain structures allows reselling, and SaaS. Medium inc SaaS is a good example of this (and all the white-label websites that use its engine). There are quite a few other web publisher that use multiple DOM objects to push their service to the clients own domain. The Microsoft SSO, email and platform can easily cover several tabs and they are organised so this works. In this context there are extra details apply:

  • Correct security headers need to be applied. Start with CSP commercial-website-features and add mentioned details. The earlier model was CORs headers see cors-headers and X-Frame-Option for direct communication.
  • There are settings for cookies that need to be configured, if they are used across the DOM objects, 11. The legal standards are described in 12 13, noting international regions must be considered, Related reading 14, cookie partitioning. Cookies are only important to talk back to the servers, and possibly to show authentication status.
    • For realistic products in the UK or EU, it is essential to have a cookie audit. These will probably be mostly made by third party services, and the audit must be current.
  • To communicate between DOM objects that are loaded at present, when we control the source is a special protocol via postMessage 15. To control DOM objects at differing times, we could use localStorage, cookies or similar (ie for login component preferences).

In the olden days services identified user devices via cookies. For over ten years, that has been legally difficult and there are other technologies. Currently (in 2026) most services make a webGL fingerprint of your device. For example 16 17 18, these are device identifiers and do not contain any PII as defined by GDPR regulations. If you mostly use the internet via a phone app, you can identify yourself by a “token you have”. . . your phone. This certainty means there is less need for identification after an initial sign-up.
