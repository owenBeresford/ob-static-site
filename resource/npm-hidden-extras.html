Context

  • I'm not sure how much use this article is generally. But if NPM docs leaves its logging at home, these steps will show you what it didn't.
  • `$package is “thing”, or “thing@semver”`
  • These notes are written for NPM v11. NPM is more stable than many JS API.
  • If anything confuses you, browse the flow diagram in 1. I have linked rather than copied for a better internet.
  • Most NPM configuration is done via package.json [but not all]. Keywords supported are documented in docs. I often add comments into the scripts section by items similar to ` "#ignore this line 1”:“blah blah note about the following script blah blah” `. Technically JSON doesn't support comments, but this hack helps.
  • Using npm forces a semver library to be present (bonus!). Be aware of these rules node-server 2 npm and if they differ from XYZ platform that you normally use.
  • WARN: On docs.npmjs.com, the NPM version selector is stiff, and you will probably need to select it twice to get the correct version.
  • Drive with nvm git to set Node (#leSigh win32 again)

ASIDE that I forget
`export NODE_ENV=production; npm i `
is recommended for operational concerns on Cloud to reduce deployment costs, but this disables many tools.
Various frameworks will stop writing to the log when this is set. DO NOT FORGET that you set this in long-lived shells.
Probably sensible policy: only do deployment tests or real deployments in short lived shells, `exit` after the step change.

Lesser known facts

  • ls -l .npmrc
    1. A hidden file docs that is used to enforce side effects :-)
  • `npm ls $package`
    1. This shows local copies of the named package.
    2. It also shows all the “unnecessary”/ dupe copies.
  • NB: do not accidentally leave NODE_DEBUG set whilst using NPM, or your term is heavily flooded.
  • `npm config list --json`
    1. A way to list several different configs and settings as a group docs
  • `npm install --force $package`
    1. Probably everyone does know this one.
    2. To limit use of --force, read about alternatives docs.
  • `npm pkg get devDependencies.$package`
    1. Returns the currently installed version. Could also be 'dependencies'.
    2. Empty brackets means not found.
  • `npm pkg get workspaces`
    1. In other languages, a 'workspace' is a 'namespace'.
    2. If you use Workspaces docs, this is how to list them. Again, generally this information abit awkward to find.
  • `npm view $package peerDependencies`
    1. This information cannot be seen in npmjs. This allows better decision making earlier as package doesn't need to be installed first.
    2. Strongly advise: full package name/ version to get the relevant output.
  • NPM included a overrides mask to regulate peer packages 3
    1. You can see what the impact of an override is with `npm ls` without needing to reinstall
  • `npm i --verbose --strict-peer-deps $package `
    1. To better manage the peer packages that give you grief in security updates.
  • `npm explain $package`
    1. List impact of installing named package docs. Again mentions peers
  • `npm ddp --install-strategy=hoisted --verbose `
    1. Attempt to reduce duplicate copy of packages. Probably uses the fabled tree shaking
  • `npm audit --production`
    1. for later stage projects where you only want to spend further time on service availability
  • `npm config get global`
    1. ...or other variables. Self descriptive.
  • `npm config get omit `
    1. This can be used as a mask to disable NPM features
  • `npm config list`
    1. This reports some code artefacts that NPM isn't suited to change (ie $PWD)
  • `npm audit fix --production `
    1. CAUTION purges everything for dev tools in 1 command.
    2. If doing that solves a production problem, its time to review tool use.
  • `npm i $PACKAGE_NAME --build-from-source `
  • `npm i $URL_FOR GITHUB_PROJECT --build-from-source `
    1. If you use any packages that have source in another language, this approach is needed sometimes
    2. In the version of NPM I am using, the first form works more reliably
  • the output formatting on `npm audit` is bad for humans with timescales and therefore prioritisation. `npm audir --audit-level= XXX` should be used as SOP to facilitate getting results faster. Not so much hidden, but an optimisation.
