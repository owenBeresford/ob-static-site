Observability on AI should be integrated into your other observability platforms.
This list wasn't made by asking an AI, which is why some items start “if possible”. I favour the acronym “LLM” over “AI”, as it's precise about what is happening and deflates marketing claims. When a tool's output resembles a person with dementia, should it be called “intelligence”?
If possible the behaviour metrics should be implemented without using another LLM, otherwise you are hedging volatile sources on each other. As a last resort, use a low temp LLM, not a general one.

My ideas for metrics

Initially “on the layer below behaviour” / traditional Devop plots, it is still necessary to measure the following. Assuming the service is cloud hosted, these are very quick to observe, as the cloud service has the data already setup.

  • Rolling average CPU load, probably 1min mean, and EWMA for longer term trends.
  • Unused storage for any DB with fixed volume, probably hourly is enough.
  • Network bandwidth utilisation, with clear alerts on thresholds. If the LLM/ agent isn't “in training” this would just be customer traffic.
  • Distribution of client-side IPs. Maybe more useful as Geolocation (ie region) to usage across time. Use this data for marketing and better service delivery.
  • Response time of the AI data, as this is much more variable than a traditional REST API. Common advise is graph each population segment for the response time separately. Most data packages should be able to plot the data as a frequency curve (occurrence vs the time elapsed vs real-world time of events), and add slicing for a more detailed investigation.
  • Simple/ basic profiling of client devices, for better service delivery.
  • If possible, the UTF-8 letterset (ie language script) and the UTF-8 plane of the user actual input data. I mention 'letterset' as 'alphabet' is a portmanteau of the first two letters of Greek “alpha-beta”, which is very Europe focused. The training data will need to be in the same letterset and plane. A message written by an urban Chinese culture person could be typed in Mandarin letters, or Pinjin latin1 letters. The two options are in different planes. Not everyone is a en-US speaker (ie ASCII 127), and there are better customer satisfaction levels, by reaching towards the customer and their culture.
  • Quite a few tools support several different LLM models. If this is true, logging which LLM is used.

Like a finance platform, I would suggest keeping an audit of LLM actions. This is useful for any compliance and legal discussions. When the LLM is structured more like an LLM agent, the skills/ tools should also be audited. The audit needs to be kept securely.

The actual “AI behaviour” should somehow count

  • The actual customer activity, as daily and monthly plots.
  • Same again for users (ie no active login).
  • If feasible, the above again against public IP and time. Many different logins with the same public IP probably means a simple client / server model isn't the best approach.
  • Account signups across time (ie users becoming customers), with annotation for marketing events on the timeline.
  • The number of queries to answer the user's overarching question. To use this data will require correlation with other plots, but numerically shows a strong product “working”.
  • If possible, a plot of abandonment events.
  • If the UI includes feedback streams per user query, are these used, and positively or negatively? Across time. This shows the quality of your product ~ so it's value ~ in real-time.
  • Tokens used per-request and per-response, across time. If the same service can be delivered with less tokens, this increases efficiency. There often is no need to explain terms on each query.
  • If the product is a LLM supporting tool, profiling on aggregate tokens used per product feature.
  • If possible, the average age of data sent to the customer. Is this mostly just regurgitation of the training data? If the data is often newer than the training data, is more retraining needed?
  • Rolling average query duration, probably sampled on 1min mean, and EWMA for longer term trends.
  • An important metric is “AI safety” being enforced, this should be an event stream, but not a graph. See "JonSnowLabs AI conference” as a vendor discussing this.
  • Note different regions will have different legislation, so LLM needs to be tuned per region.
  • As a followup, on humanist/ subjective data-categories, is the outputted generated data biased? Would suggest an event stream, not a graph.
  • For objective data-categories, the amount of invented data, that factually doesn't exist. I think any time an LLM outputs a reference webpage/ paper / software version / manual etc it should include the source of that data. The UI can minimise or remove items without a source. This matches agile-planning practices.
  • Important, are user sessions “learned from”, as that leaks PII and degrades data quality. Even more urgent for a general or chatbot LLM, rather than a narrow function LLM.
  • If renting the LLM, the tokens used across time. If a software update in a common phone changes the default voice or video settings, alerting and a suitable response need to occur before the next billing cycle. Users (not customers) should only be supported for a max volume of running costs, and the cost per query isn't consistent.
