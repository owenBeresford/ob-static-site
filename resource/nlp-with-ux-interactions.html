Natural Language Processing

Natural Language Processing or NLP is mostly a deterministic algorithm 1. This text is not about the other NLPs 2, or 3. This article is discussing how to build NLP into a service or App. The article stops when the user input has been transformed a bit and passed to the next software layer. Some NLP libraries are complex, as human languages are complex, so slower to execute. However, just as its not safe or reliable to use a Regexp to parse HTML 4 5, Regexp are not useful in isolation for NLP. I read quite a few “UI by free form messaging” design articles in 2022. I think this is still relevant in 2026.
I maybe atypical, but I think a keyboard is faster and easier to use in a busy room than talking. If I mostly used a mobile all day, I would invert my UI selection I think. Many marketing and product-one-up-men (sic!, normally are male though) think a typical user doesn't like typing, but they like talking.
A simple string tokeniser, or a embedding algorithm are like very weak version of NLP, but should be ignored in this discussion, as they omit the semantics. I think NLP as a form of data sanitising is a useful first step with text-based LLM solutions.

Interaction limits for NLP

  • Some forms optimise on fixed value ranges to simplify and support automation, others have a chat interface. If the user input is three select boxes and a CTA, there is no NLP is needed. The fixed input approach adds value if its necessary to specify a long rigid sentence, and there is no value in the user typing it (e.g. specifying license being used).
  • Most NLP modules / libraries I have seen are server-side, as they need a large volume of config data to operate.
  • Concurrency must be managed carefully if the user input can be large. The interpretation as a half-duplex step (ie not chat UI) means it can be performed in batch mode. The UI will need to be appropriate. As LLM services have conditioned people to accepting slow IT again, this is an easier sell than it used to be.
  • The language context needs to be known in advance, I hope its reasonable that a DE domain and DE prose in the signup would suggest a DE based interaction sequence. A random ~ say RU ~ response will just not lead to any useful result as the system cannot understand it. As a EN speaker I have privilege, as most libraries will still have EN parsing ability. However, assuming the system was also launched in a RU domain (ignoring the current real-world sanctions here), the NLP should be configured and extended to assume RU by default on that domain.
  • Many browsers support auto-complete features, there seems to be problems with some software not seeing content added by this autocomplete, as it doesn't trigger any input events. This can be worked round, but please add a test here. If a browser is restarted, a half completed form is likely to still have content, but that will not get any fresh events.
  • It would be useful if some code un-did tings like MSFT word “smart quotes” back to ASCII quotes. This transform is also applied to text passed through common Mac OSX text-editing apps. I was expecting the NLP library would recognise the token type, but not translate it by default. There are options in NPM or Pypi etc for translating.
  • If the expected outcome is several sentences, code can check if the last character is a dot/ full-stop. Without the ending, nudge for more input, and delay any relatively slow computations. Users may change focus to copy-and-paste or look something up, so a JS blur event may not the be the best trigger. For languages written without a full-stop, some other structure would need to be used.

Major constraints

  • Obviously if the user input is voice or video, traditional NLP library have no relevance or impact. An AI platform data import pipeline to a VectorDB would work better.
  • I need to research how to do NLP in CJK architecture languages. These are not covered in this article. I am confident that the smart and dedicated dev-teams in that region have built solutions.
  • Please check buffer sizes in the lower levels of your stack. Accidental fractional UTF-8 char are fatal to many string libraries. Abstraction leakage warning probably only present if your language isn't in UTF8 by default.

Working Interactions

  • One of the strengths of an NLP support is, like conversational English, it should be feasible to have implicit objects (safely!). As these are common in human languages, humans prefer to operate with them (it, this, them etc, and grammatical contractions). I feel (but haven't built at 'time of print') it should be possible to create a simplified version of an LLM context window, probably a Python dictionary, to know what the prose meant better. This models the short-term memory of humans, and the structure of English assumes this exists (and I blindly declare that other languages also follow this pattern, as humans are the same). My first cut solution is a cheap symbol replacement, however the replacement value would be a NLP token/symbol list (possibly 1 value).
    • The context will need careful persistence management.
  • The NLP module can tokenise the text entered, which might contain typos. Assuming tokenisation happens correctly (see Deutsche compound phrases as an awkward case), the structure of the input allows error correction guesses reliably. The offers of typo correction need to be different to applying the text input. It is necessary to check with the user. The following example for a restaurant ordering app, a typo of “special 2” rather than “special 3” alters the request intent by a large amount. In this scenario, typo correction is not feasible. However “speeeeeecial 3” or “sp3cial 3” could probably be corrected. This could be spelling suggestion 1, I have read good results for Murmer 2 hash.
  • Not as a correction, but transformations are useful. Example buying train tickets on mobile is easier if users can use a three letter station-code, and have it converted to the long name in the UI. For this would need to happen, showing the station-codes in the general UI is needed. A general completion feature would be able to offer options, but be less correct than if the user knew the station-code, and slower to operate. As another interaction, the above chat based restaurant app would gain from having “Home” defined in a setup screen, as the default location for food deliveries. The system would translate `“deliver special 3 to Home for 19:00”` to include the full address.
    • As narrower concern, observing the next few tokens are a time/date, and translating them to absolute values will reduce cognitive load by busy staff ie in the restaurant example `“order 4x shellfish platter, 4x crab special, 4x vegan surprise, 2x steak tartare with veg for next friday, have to to be ready to eat at 5:30."`. Is that 05:30 (not supported), or 17:30, as the first action after the kitchen opens? To deliver on this precise request, it may be necessary to run an extra shift, as none of those items could be done the say before.
  • I would interpret a message in CAPS as shouting, and lowercase it. Possibly annotate the user was shouting. In the restaurant example, shouting at a restaurant won't make it change its opening hours. Also the restaurant will probably not read the message until they are open. A contrary-wise example is a list of keywords relating to IP networking, correctly written out in caps as they are abbreviations. If internal systems are case sensitive (like PG is), cautious normalisation would help. If they are not (as MySQL is), keeping what the user entered probably preserves semantics better.
  • For a TEXTAREA input, it might add value to have a copy of last usage, tagged with the date it was used. Design this as a popup menu/ overlay, that the user can cancel to hide easily. In the context of mail templates, this helps the user. This can be done via waiting for the user to stop typing, but that lacks semantic intent.
  • For services where the user is expected to ask a question, linguistic analysis for “this is a complete question” would be useful feedback in the UI. That requires a sentence with a subject noun and at least one verb.
  • When given a free-text input some users will default to just entering keywords. This should still work, if they entered enough keywords. However, I feel the interaction style should be recorded and adapted to.
  • Matching other free text input tools, this app could support UP arrow-key for repeat last message like bash does. Alternatively, UP can be mapped to edit last message, as Signal does. The relevant choice can be made with more data about the app.
  • An interaction to consider is also allowing free-text sign-on, so no forms at all. This would make marketing people happy, but security and SRE less so. As a text stream with a context, one of the details can be “logeed-in:boolean”.
  • As an solution implementation behind the NLP layer, a valid question that the App or service cannot meaningfully respond to, should either get a fixed “I don't think that is a service I can offer” template, or claim to escalate to a human (probably no actual change in implementation steps). In a food delivery app, the app can't do anything about inflation or income tax for example. There is no damage rejecting the request. However that same app should escalate to a human if the user mentions “allergies” (in EU, JP or CN, but not needed the USA).
