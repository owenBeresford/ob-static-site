Intro

In apps, there are two areas that need testing most strongly:

  • Logic / business logic, as humans are weak with logical thinking,
  • “flakey corner-cases”. Browsers are a large tool and have an above average number of flakey corner-cases. As security structures are created, they add more flakey corners and more complex ones, as JS often doesn't work a well in this case (so the security feature cannot be bypassed).

Every test tool can test business logic, so this is ignored in the rest of this article. See the end of the other pages on testing if ignorant. This entire site is very boring if SWE isn't your trade.

Flakey corner-cases are a leading cause for manual testing, as this allows some progress. It is needed to have a careful review of what is happening if the flakey corner-case lacks sufficient docs. Many of these corners are fiddly.

AFAIK, 'a corner case' is a term borrowed from civil engineering 1, as corners obviously stick out, and get bashed more than flat sections of wall.

Current list of corner cases

The following are known areas of JS-inside-browsers that are harder to test. This list will get larger, and the focus is on solutions not cataloguing “JS being awkward”, again.

  • Investigating certs from browser JS,
    • Easier from outside the browser. At a minima, any Node process can integrate OpenSSL CLI 2 3 tools for fun and profit.
  • Server availability,
    • Some OSS work git, but not much data possible.
    • Easier from outside, see one or more 3rd party SaaS adverts here
  • JS Worker* features (aka Threads in other languages).
    • Some OSS git 4
    • In other languages, I would organise to run any logic from the Worker module in the main test process, and then a second set of tests to start and stop threads and pass messages. Inside JS, the Worker script would need to be cut-n-shut 5 into a normal object.
    • Noting the Worker functions are not public or exported, as they do not need to be.
  • Session jacking for legit security purposes ie to force login to a hotel wifi.
    • A tool for manually doing traffic redirection 6. Some notes 7.
    • In my first employer I built a small module that performed enable transparent redirects if certain data was found in a provisioning DB. This encouraged payments from people with expired card details logged.
  • Direct Keyboard events,
    • But you can test form inputs by DOM manipulation docs, and other libraries.
    • I have made a maquette, for keyboard interaction in Navbars 8. This is soo much code for basic interactions using arrow keys and space/ escape that should just work.
    • Games and tools like gmap want to use direct key events docs, and probably to normalise between different clients.
  • “background tab events” are happening correctly,
    • As soon as a tab is in the background JS timers go weird and slower 9. The slower effect is an architecture detail to save batteries on portable devices. There is a well known step algorithm for aligning steps [XXX] which helps normalise this.
    • This can be observed from your server, if the background action includes server traffic. Or in a persistent log somewhere (maybe SaaS, maybe localStorage or maybe DOM additions).
    • Some tips for JS 10 11 in Chrome.
  • HTTPS only features require actual real certs, or get loads of warnings.
    • This is manageable due to letsEncrypt 12 13 14, hence I moved it last.
    • Due to what a cert is, its necessary to have public DNS names. Another option is an extra local CA 15
    • I have a captive browser project to perform BDD tests inside the HTTPS/ SSL git, but to get better quality I need to replace Playwright (not the Python version) with Puppeteer (not the Perl version), so I can use a wider variety of browsers.
