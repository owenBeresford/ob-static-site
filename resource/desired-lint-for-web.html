I am writing this as a declarative list of wishes, then mapping options in ESlint manuals. I expect this will grow longer across time. Having coherent structures for what needs to be validated should lead to better quality. Most of this can be achieved by strapping together several currently used tools, as my thoughts are not original here.
I am using lint as a generic term for static analysis, if there is a tool that helps this list of goals that technically isn't a lint, it's still useful. The goal of the described tool is to reduce the amount of knowledge needed to support users, possibly customers goals. Just click the “run test suite” button.
In a mature solution, the output should be loggable in various channels (STDOUT, Jira, batched in email etc). For this platform, as there will be multiple browsers running, reading the JS console is not a viable logging solution. “Many of these items are obvious” is an obvious retort, however an actionable message ~ which is probably about generated text ~ adds value. Dev staff are often moving quickly and tired. The software will not blink, and the devs should do.
As the article is basically a big list of validation ideas, if a site is good and passes all the tests, maybe emit a “all tests pass” like unit-tests frameworks do, but not log the positive result a million times. Engineering these conditions is a large surface, to to delver, I would suggest recycling older OSS where possible. I will do a literature survey for the current testable metrics ~ ideas are presented inline to reduce total word count.

Outcomes of the tool

As a business process, if this was applied to an average wordpress branding site, and the tool discovered 8,000 errors, what next? The wordpress administrator could see if there was a new version of plugins used, or swap to another theme that included quality. A mature test platform would have a process for a list of devices, possibly more than a busy admin had time to test against personally.
Reference use-case (real-world experience): In 2012 I joined a web-agency who managed over 300 domains, as part of a batch of staff to increase quality and scale as they had an expanding client list. This agency had some 25 YO code, and some 1 YO code. Expectations and standards have gone a long way in that duration. A tool to auto-log various sanity checks would have improved production process, and reduced hiccups.
Could the checks be done via an LLM? Yes, sometimes, but non-determinism is a limit for validation checking. If I built a 1,000 skills for an LLM agent, could the agent validate the site-under-test? Yes, but the 1,000 skills would also allow validation via Jenkins or something. Without this long list of skills OR a very long prompt, that would match this article, I wouldn't sign for a general LLM validating production code.

Tests via pre-deployment static-analysis

These checks/ tests do not need the domain name to operate.

  • Does the source parse correctly? ~ a general malformed typing check. BUT THIS CHECK HAS A FILE NAME AND LINE NUMBER, JS build tools often skip the details due to multi-stage parsing. Direct unit-tests should catch this problem first ~ and execute faster ~ however it is essential to trap this before the users see it.
  • A generic “do all local or relative URLS work?" check.
    • LightHouse may implement this. Assuming platform has access to a CLI shell, `wget --spider` works very well 1, and there are various SEO tools can offer this if needed. The reason for using wget is the reporting is exactly as needed for this check.
    • This check was urgent for AI made websites in 2023-24, where the links often are not implemented.
  • Are the HTML files using the most relevant JS loading method? ie a module, possibly defer attribute and encourage MJS suffix. This check may need to vary on situation, so it needs to be nuanced.
    • This is HTML parsing, if in Node, would look at `node-html-parser`, or similar. If in a browser use a new TEMPLATE element. Extract attributes of the SCRIPT elements.
  • Warn if same dependent URL imported more than once (in some cases like Google Analytics this might be correct).
    • See last check for process
  • Is correct version of HTML has been used? AFAI-can-imagine, always use the current HTML5 edition, aside from people you know use old Outlook (modern Outlook uses a webrowser again, but not MSIE5, so users are safe).
    • See last check for process
  • Is the webpage furniture present? ie a `robots.txt`, with correct file permissions. See commercial-website-features for my 2023 recommendations.
    • Can use LightHouse for an implementation. Or a manual built list.
  • Is the HTML file size too large? As mobile view will be slower with larger files (guess over 100KB)
    • file system library, or HTTP header `content-length`
  • Are there too many elements in HTML files? As mobile view will be slower with larger counts (guess over 10,000 nodes).
    • in a browser this is easy. In node again use `node-html-parser` and `querySelectorAll`
  • Are there vast numbers of images? As it will be slow for older machines, or slow internet users (guess over 100).
    • Use same approach as last
  • Is there a large number of dependant files? As it will be slow to download (guess over 100, note deps of CSS and deps of JS and direct deps, images and fonts). This number will surprise devs and users.
    • #TODO, laborious.
  • Is all the human text spelt correctly? Extract all the human text, and spellcheck it. This expression is to include the obvious paragraphs, alt-texts, title attributes, CSS Content injected from data-attributes, the Zoho style HTML islands in JS files etc.
    • Some spellcheck libraries in JS are `typo-js-ts`, `spellchecker`, `@cspell/eslint-plugin` etc. I see that most of these just appeared about 5-6 years ago. Due to needing to manipulate files, the spellcheck libraries are normally Node only, but the text can be streamed to an API, and returned. Wrapping Hunspell docs docs is common, although after win7 there is a module API for spellcheck available. To support the return a patch format will need to be designed. In historic PHP solutions that I used, this was a new HTML response page, with select boxes embedded for spelling alternatives.
  • Is the HTML valid?
    • spelt `html-validate` :-)
  • SEMrush style meta-data checks ie is the page title a sensible length?
    • Look at `siva01c/seo-tools` or `SEOmator`


  • Taking the site-under-test as a whole, are the titles well selected / managed so users will go to their goal efficiently, rather than a random walk? Unique feature, AFAIK. Look for very similar titles, as this makes goal seeking hard. Ideally look for very vague titles. Likewise, but that the latter is abit subjective.
    • See `scikit-learn`, `TF-IDF` + cosine similarity for initial work.
  • Do the UTF8 symbols chars work? There are known not to work symbols in Safari or Firefox etc (these are classes or planes of symbols). See currency symbols, flags, emojis, checks/ ticks and copyright sign as initial check points.
    • Safari uses a different encoding to render for HTML symbols. See colourise-emoji
    • This will be a big data collation exercise, no solution to hand. This item needs contribution capacity on day 0.
  • Has text from a DB (or similar) included HTML which has been mangled by the render pipeline?
    • A regex should work, looking for `&lt;[A-Za-z]+ /&gt;` and `&lt;[A-Za-z]+&lt;\w+&lt;/[A-Za-z]+&gt;`.
  • Has data read from a DB been mashed badly? The result would be broken and unreadable letters, probably a empty square box. Or other possible sources, but DB seem to be the most common failure point. ...Its now 2064, we still need to check that big-corp legacy systems haven't still emitted old 2byte encodings, designed for countries that no longer exist...
    • Try the regex in w3c as first guess solution.
  • Do images have sizes attrib set, to reduce screen reflows?
    • html parsing, see above
  • Do images have RWD options to best support users across devices (eg a IMGSET or PICTURE)? See html5-img as a simple reference.
    • Unless SVG or other vector, as they will scale. Unless the size settings in the SVG element are awkward.
    • html parsing, see above
  • #TODO Work out if some sort of check for background-image CSS vs IMG is feasible or useful. I use IMG for things I want to show in a B/W printout, and in a screen-reader. So diagrams, not 'smiling man with coffee #44' from an image library.
    • Maybe, if you think an ARIA-hidden or role=decoration might be relevant, than the IMG should be a CSS background, and disabled in the above situations. Taking an image from a image library does imply that its not a graphic for factual information.
  • Are there duplicate CSS attributes?
    • as `Stylelint` does, and I assume `ESLint` with a config
  • Is there deprecated CSS1 float? to be replaced with flexbox or grid.
    • `ESLint` can do this.
  • Is the best colour notation used? Rewrite older colour notations for better ones.
    • `Stylelint` and `ESLint` do this.
  • POSSIBLE CSS warning to deprecate absolute CSS length units for relative units that make RWD faster and easier. Should be disableable, as might get annoying.
    • `Stylelint` and `ESLint` do this.

Tests to automate at run-time

In theory, I can set the screen details (resolution, and dimensions) on a Chrome instance via CLI arguments. In practice this didn't behave as I expected it, and this feature may have been soft-removed. However, a Docker instance could have the screen details set, in it's basic hardware emulation. A VMware or QMU instance would emulate better, but cost more real computer resources.

  • As a test suite, this tool should either auto-explore the whole site-under-test, or check a supplied list of URLs. The second approach is needed for incremental testing on incremental changes.
  • As a manual test detail, I conditionally add a extra line of CSS that sets the border on every element. This makes it more clear which element is breaking the layout in a given situation, so faster to resolve.
  • Are the URLs fast enough for good UX? On each probable network option.
    • Look at LightHouse as a prototype of this test.
  • Do the 3rd party URLs on deps work from that server (e.g. CDN assets)? This needs to show valid auth steps and caching is correct.
    • The actual effective page load speed (recycled JS snippets are a good example of poor performance, especially loaded in sync mode).
    • Again look at LightHouse for an implementation example.
  • Is a page on a site seems to be older than other pages? This is not an error, and it must be possible to disable this.
    • Mapping the URL and `Last-Modified` headers is probably useful here. Probably the value for “is this old?" will be specific to each organisation, so need to be a config setting.
  • Suggest legal notes warning, curated for the current country. This must be disableable, and settings must somehow include setting the country. Example a UK based fintech site should list relevant options from: Copyright owner, complete company name and a legal-process contact address, FCA number, the prudential registration, Privacy notice link, Cookie Policy link, Data Protection Policy link, Accessibility link, FSCS Protection statement, an anti-slavery statement and possibly a carbon reduction notice link. Add a warning if the data is absent, or links to it do not work. Also warning (not error) if these docs seem to be very old assets.
    • The above link checking code will work, but building a phrase detector to locate the links is needed.
  • Does the content languages match the meta data tagging?
    • and does this match the culture expected in the domain ~ eg its reasonable an AF TLD would include some Afghan text, as its a country specific domain. There should be no language assumptions about ISO TLD like '.com'.
  • Is text a readable size? (on range of devices).
    • Select an element, select the currently active CSS against it, `getComputedStyle` 1
  • Does the selected font have all the letters / glyths necessary in it?
    • An open tool that does this check font-character-checker.
    • If your site would like a font that omits a currency symbol or something, those specific glyths can be imported as CSS font-family override, so there are no hollow-boxes symbols in the result UI. This can be looked up as glyph‑level font fallback, if editing the font isn't possible due to licensing.
  • Do you have FOUC 2 ?
    • LightHouse helps here. JS support for this analysis offers “load” event 3, and PerformanceNavigationTiming 4. I think LightHouse use LayoutShift API 5


  • Are all the important artifacts “above the fold” in the first screen-full of data? A wise dev-team would do this analysis in the wireframe stage, as its more clear about importance of each component at that point. This is a means to guesstimate bounce rates ahead of publication.
    • Some marketing teams add “cash value of page” notations, to measure impact of user actions. If they did this with each component, rather than page, this data would be accurate and meaningful.
    • I can invent heuristics for detecting important items, but this has no defined implementation at present. Feature not seen elsewhere, but must be performed manually by teams.
    • This check is harsh on small phones like an iphone5.
  • Ia there a good “artifact density per page”? Extremes are less good to read (no idea how, todate. Possibly look at element screen volume vs total screen volume). A wise dev-team would do this analysis in the wireframe stage.
    • If the lowest ARTICLE or similar element has a coloured background, and elements inside it had a reset background, this would be a visual guide. But being able to convert this to number makes it automatable.
  • Do your colours work in all browsers? Noting Safari has some awkward maths limits on computed alpha channels being floats, not ints. So being an example needing this check.
    • Render the page, ?? somehow detect if wrong. Converting a HTML doc to a canvas will deliver data, and catch some errors, but not all of them.
  • Is Colour contrast between FG and BG large enough? On a range of devices.
    • See css-palette-extractor as a theory. I wrote maths for the actual delta in git.
    • Via a $PROCESS, get a list of all the colours used in the software under test, and check the colours in 3rd party tools as well. If GMap is the problem the colours can be overridden, I hope other systems would have a colour override too.
  • Are any HTML elements superimposed? Especially when the lower one is or contains links.
    • This could be implemented by looking at the JS `getBoundingClientRect`. In theory, I should use the intersection API 1 as it as now widely supported.
  • Are there forms or similar data-entry with no visible or actionable submit sigil?
    • If there are no hand-made forms, this shouldn't occur.
    • It will be possible to create a working UI that will fail this test, but that isn't the point.
  • Are elements larger than browser size? When browser is sensible size.
    • See last check, but the larger boundary is the window size.
  • Are there pages of vertical scrolling with no content showing? Important check, must be on range of devices. This occurred to me in Safari with code that works in Chrome.
    • Note, the element location maybe the altered by CSS , JS or the general composition algorithm.
    • The location on every element would need to be checked. It might be possible to make some assumptions to reduce the element count (in particular, skipping the LI of an UL or OL). This can reliably be built from data the browser supplies, see `setScrollOffset`, `pageYOffset`, and `getBoundingClientRect`. There is an older module in npm `in-viewport`.
  • All the WCAG check items not mentioned above. Should be imported from an existing WCAG tool.

Quite a few of the unique items in this list are applying a number to design heuristics that the dev team probably applies without converting the current DOM state to a number.
